# Profile 借用 CLI 安装树的核心依赖，启动前只报告风险

## 背景

DSH 的核心运行时包（`@deepseek-ai/dsh`、`dsh-*`、`cordis`、`cordis-*`）由 CLI 的
依赖树提供，一个进程里只该有那一份：工具调度器是模块级 `Symbol`，
`@deepseek-ai/dsh-app-boot` 是模块级 WeakMap，状态挂在模块身份上，载入两遍就各查不到对方。

Profile 也可以有自己的 `dependencies`。如果 Profile 的 `node_modules` 里又出现一份核心
包，Node 会就近解析到它，于是同一个进程里出现两代核心：agent loop 在 `ToolRuntime` 上查
调度器得到 `undefined`，这个 Profile 的每个工具调用都以
`Cannot read properties of undefined (reading 'prepare')` 失败——加载时没有任何报错，
也没有线索指向是哪个包重复了。

启动器会建很多版本与实例，是最容易造出这个状态的程序，所以它在启动前查一遍。

## 决策

**Profile 不拥有核心依赖：它借用所绑定版本 CLI 安装树里的那一份；启动前查一遍，只报告。**

- 启动器从不把核心包加进 Profile，核心包由 CLI 安装树提供；插件的装与卸都走运行中 DSH
  的原生管理（ADR-0001），启动器不代它改依赖。
- 启动本机实例前做一次依赖树预检（`doctor::inspect`），看两件事：
  1. 所选版本与 CLI 树里 `@deepseek-ai/dsh` 的版本不一致，或者读不到这份信息 → 提示级。
  2. Profile 的 `node_modules` 里出现核心包 → 提示级；这一份的版本与 CLI 树里的不同代
     → 错误级（就是背景里那个静默失败）。
- 报告是建议性的：只上报、记日志、在界面上显示，**不阻止启动**，不改依赖，也不替用户修
  （`doctor::log_report` 与 `instance://health` 事件）。
- 只查本机实例：版本树与 Profile 在实例所属的那台机器上，而本机的 `fs` 读远端路径会读到
  这台 Mac 上同名的地方（ADR-0006）。远端实例跳过，给一份空报告，而不是报一个错的。
- 诊断入口与启动前的检查是同一份实现：`check_instance_health` 命令和 `start_instance`
  的预检都走 `doctor::inspect`。

## 后果

- 核心包的解析必须维持同一来源。Profile 里出现核心包这件事本身就要报，哪怕版本与 CLI 树
  一样——它不是版本问题，是「不该有」。
- 普通工具库不按核心包处理：`cosmokit`、`schemastery` 这类插件常用库不参与 DSH 的调度
  与单例状态，报它们只会制造噪音。
- 结论分两级：重复核心包（同代）是提示，混代是错误。前者可疑，后者一定会坏，页面上要分开。
- 用户仍能启动有问题的实例进去自己诊断。本机是用户自己的桌面，他有上下文也有动手改的自由
  ——与 ADR-0005 对 Node 版本「只告警不阻止」同一条立场。

## 备选方案

- **启动器替用户清掉 Profile 里的核心包**：被否。那等于启动器改写依赖树，而且「哪个包多余」
  没有可靠判据；上报让用户自己卸（插件的装与卸本来就是 DSH 的事，见 ADR-0001）。
- **让 Profile 自带一份核心包**（把核心包钉进 Profile 的依赖）：被否，就是背景里的坑。
- **发现混代就拒绝启动**：被否。会把「能启动但工具全坏」变成「完全动不了」，用户连进去看
  一眼的机会都没有，而自检本来就是建议性的。
