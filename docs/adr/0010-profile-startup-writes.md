# 启动器只写启动必需的 profile 事实，不写插件状态

## 背景

ADR-0001 把「启动器不写任何 profile 文件」写成了绝对结论。它对**插件状态**仍然成立，
但作为字面说法已经过时：启动之前，启动器会往 profile 目录里写三类东西——受管 lan-bind
块里的端口、`pnpm-workspace.yaml` 的 `storeDir`、`.npmrc` 的 `auto-install-peers`；
复制模板之后还要擦掉模板里钉住的端口。这些写入在 `profile.rs`（`assert_profile_lan_bind_port`、
`scrub_profile_port_pin`）与 `plugins.rs`（`ensure_profile_store_pin`、
`ensure_profile_npmrc`）里，远端在 `process.rs` 有两个同构实现
（`assert_remote_lan_bind_port`、`pin_remote_profile_store`）。不写下来，下一个读
代码的人会以为这是回归，然后把它删掉。

## 决策

**启动器不写插件状态；只写「启动这件事本身必需」的 profile 事实，并且写在那台机器上。**

1. **端口**：补丁文档里那个受管 lan-bind 块是顶层补丁行，优先级高于命令行 `--port`，
   而插件要等 web 服务绑定完成之后才重新断言它。不同步，改了端口要等下一次启动才生效。
   所以启动前把本次实例的端口写回那个块（不钉端口的实例写 `0`，交给系统分配）；
   **没有这个块就不动**——未受管的 profile 靠 CLI 参数，那里本来就没有覆盖。
2. **pnpm store 与 peer 策略**：运行中实例的插件管理器自己起裸 `pnpm`，看不到启动器的
   `--store-dir`；profile 自己不记，装插件就报 `ERR_PNPM_UNEXPECTED_STORE`。同一个裸
   pnpm 在 `auto-install-peers` 打开时还会把核心包再拖一份进 profile，doctor 报的重复
   Symbol 就是这么来的。这两条写进 profile 自己的 `pnpm-workspace.yaml` 与 `.npmrc`，
   取值规则见 ADR-0012。
3. **复制模板后擦端口**：web 模板把第一次绑定的端口写进了补丁文档，照抄会让派生实例抢
   同一个端口。所以复制出 `__temp__` 之后先擦掉那个钉。
4. **尽力而为**：这些写入失败只记日志，不阻断启动——代价是这一次或下一次启动的端口，
   或者插件页里装不上东西。它们不是启动的前置条件。
5. **在归属那台机器上、用同一轮读到的文档写**：远端不照本机路径写（那会写到一个同名的
   本机目录），一次启动一次往返。

## 后果

- **ADR-0001 的「不写任何 profile 文件」应读作「不写插件状态」**：插件列表、启停、卸载
  仍然全部走运行中实例的 `/api/pluginManager/*`，没跑时仍然只有文件投影；它的其余结论
  不变，本 ADR 只收窄那一条。
- profile 目录里会出现启动器自己的键。它们回答「这个组合怎么被启动」，不回答「装了什么
  插件」——把两者混在一起，正是 ADR-0001 那条 bug 的成因。
- 用户手改受管块里的端口会被下一次启动改回来（块自己的注释就写着不要手改）；要改端口请
  改实例的端口设置。
- 这类写入失败的症状是「启动成功、插件页却装不上东西」；先查 `pnpm-workspace.yaml`。

## 备选方案

- **完全不写，让用户自己在 DSH 里改**：被否。DSH 重启时插件会把端口改回它记的那一个，
  文件与界面从此各说各的。
- **也给插件的 pnpm 传 `--store-dir`**：做不到。那是实例进程里的 pnpm，不是启动器起的。
- **继续在启动器里写插件条目**：被否，正是 ADR-0001 记录的那次文件写坏事故。

## 追加（2026-11 注释清理）

- 受管 lan-bind 块用 @linxin666/dsh-remote-web-ui 插件自己的标记行圈定：标记必须与那个插件的 lan-bind.ts 逐字一致，认不出标记就什么都不改——猜一个块出来改，等于又替 DSH 写它的文件。
