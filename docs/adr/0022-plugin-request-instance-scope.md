# 插件请求交给入口实例，否则交给第一个匹配的实例

## 背景

插件的列表与启停归运行中的 DSH（ADR-0001），而请求要先找到「在跑这个 DSH_HOME 与这个
Profile 的那个进程」。

同一个 HOME、同一个 Profile 可以被两个实例同时跑（同一版本多实例、一个版本绑多个 HOME，
见 ADR-0003）。只按 HOME 与 Profile 取「第一个匹配」会把操作派给用户没在看的那个进程——
切一次补丁层，生效在另一个实例上，页面显示的却是这一个。

反过来「只认入口实例」也不行：入口实例停了，另一个匹配实例还在跑，页面就永久失去管理
能力。

## 决策

**请求带上入口实例；入口实例优先，它不匹配时退回首个匹配；应答的那个实例的 id 回给页面。**

- `list_plugins`、`set_bundle_enabled`、`remove_bundle` 都传入口实例 id（页面从哪个
  实例打开）。后端 `process::running_for_profile` 用它排序候选：入口实例先，其余按登记
  顺序；入口实例自己不匹配（没在跑、跑的不是这个 Profile、或者属于别的 HOME）时，退回首个
  匹配。
- 回给页面的 `PluginView.instanceId` 是**实际应答**那个实例，不是入口实例：两者可以不同。
- 能不能管理由应答进程的凭据决定——运行表 URL 里的启动 token，与进程是谁起的无关：被系统
  接管但 token 还在的照常可管，只剩空 URL 的才只读。
- 页面要能说清「在改哪个实例」：入口实例与实际应答者不同时，不能混成一句。

## 后果

- mock 里的 `resolveRunningInstance` 抄同一条顺序（先入口、后登记顺序），否则预览与桌面
  的行为会不一致。
- 只读状态与「谁应答」无关：`not-running`、`adopted`、`unreachable` 三种都没有应答者，
  它们说的是「没有能应答的进程」，不是「应答者是谁」。
- 现状缺口：`PluginPanel.vue` 只把入口实例传下去，拿到的 `PluginView.instanceId` 还没有
  渲染出来。这条契约的后一半（页面说清实际响应者）要补上，否则用户看到的仍是「我以为在改
  哪个」。
- 同一台主机上实例不重名（ADR-0003），所以会撞上的只有「名字不同、跑同一个 HOME 与
  Profile」的实例；这种情况下入口实例通常就是应答者，兜底那条只在它停了的时候起作用。

## 备选方案

- **只按登记顺序取第一个**：被否，见背景。
- **只认入口实例**：被否。入口实例退出后，其余仍在跑的进程反而在页面上失去管理能力。
- **前端自己挑应答者**：被否。前端看不到运行表与 token，只能猜。
