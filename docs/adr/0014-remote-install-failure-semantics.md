# 远端安装只在证实失败之后才清理目录

## 背景

远端的安装命令是脱离 ssh 会话跑的（`setsid`，输出写在那台机器上的日志文件里）。启动器
能知道的只有两件事：日志里写了什么，那个进程还在不在。读日志失败、ssh 超时、连接断开，
说明的是「启动器与那台机器的连接」，不说明「那条命令怎么了」：它可能刚开始，可能还在装，
也可能刚刚装完。把这种情况当成失败去清理，就是丢掉一个刚装好的版本——issue #14 的事故
就是这样：一次读日志超时之后目录被删了，而那行 `<<<DSH-EXIT>>>0<<<DSH-END>>>` 已经写着装成。

## 决策

**远端安装的失败分两类，在类型上分开；只有确凿失败才清理那台机器上的目录。**

1. 一个步骤的失败带 `log_lost`：拿到退出状态、或进程已不在，算**命令自己失败**；读不到
   日志算**读不到结果**。`RemoteStepFailure::discardable()` 只对前者为真。
2. 清理的判据就是 `discardable()`：确凿失败才删那台机器上的版本目录与 pnpm 缓存（清缓存
   是为了下一次重试有个干净起点）；读不到结果时目录原样留着。
3. 读不到结果时如实报「没能确认」，并写明那台机器上可能还在装。启动那条命令的调用超时也
   算读不到——命令可能在超时之前就起来了。读日志超时先重读（两次），仍然读不到才升级成
   `log_lost`。
4. 没有登记的版本不算装成：不写版本记录、不登记 PATH；主机恢复之后用户可以重装或检查。
5. 同一条判据用在每一个远端步骤（克隆、pnpm install、构建）上，不只最后一步。

## 后果

- 失败的远端安装可能在磁盘上留下半成品目录，要靠用户重试或手工清。这是为「不删掉活着的
  安装」付的钱。
- 页面与任务日志必须把「安装失败」与「不知道结果」说成两件事，否则用户不知道该等、该重试，
  还是该上那台机器看一眼。
- 留着的目录不是垃圾：下一次成功安装会覆盖它，而先看一眼日志往往就能判断它走到哪一步了。

## 备选方案

- **任何错误都清理**：省磁盘，但会删掉正在写入、或刚装完的版本——正是 issue #14 的事故。
- **任何错误都保留**：失败重试时半成品树会让 pnpm 的报错变得难懂（缓存里的坏条目会让之后
  每次安装都报 integrity 错误），所以确凿失败还是要清。
- **清理前让用户确认**：后台任务没有这个交互面，用户也没有判断所需的信息。

## 追加（2026-11 注释清理）

- 本机安装失败与远端不同：子进程就在启动器手上，失败即是确凿失败，一律清掉版本目录（连同这条路径写下的 allowBuilds 清单）后从干净状态重试；这一步发生在版本登记之前，目录还没有任何记录引用，所以没有「删掉活着的安装」的风险。
- 远端安装失败按那台机器的日志证据分类，而不是只报退出码：内存不足、连不上 registry、依赖的构建脚本失败、其它——前两种在进度条上几乎一样，修法却相反（加内存/换机器 vs 修 registry 或网络），必须分开；内存证据先判，因为撞到内存上限的日志里往往带着网络重试；构建脚本失败指向工具链（缺 node 的脚本以 127 退出），不是重装依赖。
