# 认定端口上的进程是 DSH：只认字面的 dsh

## 背景

启动器有几处必须回答「这个端口上跑的是不是 DSH」：启动前的端口预检（占着端口的是 DSH 就
收养，不是就报占用）、启动后的收养（换了启动器或被强杀之后认回原实例）、停止时追停替代
进程，以及远端那一半同样的判断。

判据放宽会把别人的服务当成自己的实例，「停止」于是可能误杀别人的进程；收紧到只认进程名，
又会漏掉真实存在的两种形态。

## 决策

**只把字面「dsh」（进程名或命令行，忽略大小写）当作 DSH 的证据；不认 `node`、`bin.js`、
`--profile`。**

- 进程名与命令行都读（本机 `ps -o comm= -p <pid>` 与 `ps -o args=`，远端同样两个字段）。
- 命令行必须读：单文件打包的 DSH 名字不是 dsh（Python 打包的那种跑成 `MainThread`），
  argv 里才带 `…/dsh/lib/bin.js`；npm 安装的那份跑成本机的 `node`，argv 里是
  `…/@deepseek-ai/dsh/…/bin.js`。只看名字会把这台 DSH 判成「别的进程占着端口」，页面显示
  已停止。
- 反过来，`bin.js`、`--profile`、`node` 这些标记属于无数 Node 工具：凭它们认定 DSH，就
  把「停掉这个端口上的东西」的权限给了任何 Node 服务。
- 本机与远端共用同一条规则：远端 `ps` 读到 command/args 后，判断的还是同一个函数
  （`process::looks_like_dsh`）。

## 后果

- 判据是一个忽略大小写的子串判断：宽到覆盖各种安装形态，窄到不认通用 Node 标记。名字与
  命令行都不带 dsh 的 DSH 认不出来——这是有意的，认错比认不出贵。
- 端口被别的进程占着时，页面要说「被 pid N（名字）占着」，而不是含糊的启动失败；随机端口还
  必须先用记下的 token 认证成功才认领（ADR-0007 §2），这条不因为「名字像」就跳过。
- 停止已经用上它：追停替代进程时只停「端口上、名字像 DSH、且核对过启动时间」的进程
  （ADR-0017）。
- 改这条规则要同时想本机与远端：放宽 = 可能停掉别人的服务；收紧 = 漏掉打包形态。

## 备选方案

- **只认进程名**：被否，见上（打包形态与 npm 形态都认不出来）。
- **把 `node` 也算作证据**：被否。端口上大同小异的 Node 服务太多，收养与停止都会误伤。
- **只凭运行表里记着这个端口**：被否。运行表是提示不是权威——进程可能已经退出或 pid 被复用，
  端口可能被别的程序接管。
