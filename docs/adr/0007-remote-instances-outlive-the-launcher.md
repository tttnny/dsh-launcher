# 远程实例不随启动器退出而停止

## 背景

本机的实例是启动器拉起的子进程，规矩是「退出启动器就停掉」（`process::kill_all`），
只有被收养的外部进程活得比启动器久。远程照抄这条会很荒诞：关掉笔记本上的启动器，
服务器上的 DSH 跟着一起没了——把 DSH 放到服务器上跑，意义正在于它不依赖你的桌面。

## 决策

**远程实例脱离启动器的生命周期：起成独立会话，启动器退出时不停它，下次启动自动收养。**

1. 启动时不在同一个会话里（远端用 `setsid`，stdin 接 `/dev/null`，stdout/stderr 追加到远端
   日志文件），因此 ssh 连接断开、启动器退出都不影响它。
2. 退出启动器时不给它发信号。下次启动在后台认领一遍，与本机 `adopt_surviving_instances`
   同一件事：钉死的端口上只要有 DSH 样的进程就认领；随机端口必须先用记下的 token 认证成功
   才认，否则那个端口可能是别的程序。
3. 远端有它自己的一份运行记录（`<远端数据目录>/running.json`），记下 URL、token、profile
   与 pid（pid 连同 `/proc/<pid>/stat` 里的启动时间一起记，停止前先核对，避免 pid 被复用后
   误杀）。这份记录是「启动 token 跨会话记住」那条契约在远端的落点：不写它，启动器一重启
   就丢掉 token，插件页从此只剩「由系统接管」那条死路。
4. 停止只在用户点「停止」时发生：按 pid 发 SIGTERM，然后轮询确认。

## 后果

- 同一台主机上的实例，行为像「被收养的外部进程」，不像「启动器拉起的子进程」。「停止」
  是唯一的停机路径。
- 远程主机上出现启动器不知道的实例是常态（用户自己 ssh 上去起的、别的启动器起的），
  所以「能不能管理插件」仍然只由 URL 里有没有 token 决定，与进程是谁起的无关。
- 界面上的「已停止」与「主机连不上」必须分开显示：状态说错会让人做出错误的动作——
  看到「已停止」就去点「启动」，于是在服务器上起了第二个（这正是收养机制存在的理由）。

## 备选方案

- **照抄本机，退出即停**：被否，见背景。
- **主机记录里给一个「退出时是否停止」的开关**：被否。同一个开关在两种情形下的默认值会
  相反，等于让每个用户先做一次他没有依据做的选择；而这两条规矩各自在自己那台机器上都是
  合理的。
