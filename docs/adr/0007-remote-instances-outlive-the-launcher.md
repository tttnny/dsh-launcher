# 远程实例不随启动器退出而停止

## 背景

本机的实例是启动器拉起的子进程，规矩是「退出启动器就停掉」（`process::kill_all`）；被收养的
外部进程本来就不是启动器的子进程，退出时只尽力发一次 SIGTERM，死没死不由启动器说了算。远程
照抄这条会很荒诞：关掉笔记本上的启动器，服务器上的 DSH 跟着一起没了——把 DSH 放到服务器上
跑，意义正在于它不依赖你的桌面。

## 决策

**远程实例脱离启动器的生命周期：起成独立会话，启动器退出时不停它，下次启动自动收养。**

1. 启动时不在同一个会话里（远端用 `setsid`，stdin 接 `/dev/null`，stdout/stderr 追加到远端
   日志文件），因此 ssh 连接断开、启动器退出都不影响它。
2. 退出启动器时不给它发信号。下次启动在后台认领一遍，与本机 `adopt_surviving_instances`
   同一件事：钉死的端口上只要有 DSH 样的进程就认领；随机端口必须先用记下的 token 认证成功
   才认，否则那个端口可能是别的程序。认证在**那台机器上**完成（在那边的 loopback 上花掉
   token），因为远端实例绑的是那台机器的 `127.0.0.1`：从本机问同一个 URL 会问到这台 Mac 上
   的另一个服务（ADR-0006）。占用的探测、进程名的读取也都在那边（`ss` 与 `ps`）。
3. 远端有它自己的一份运行记录（`<远端数据目录>/running.json`，按实例 id 索引
   `{url, token, profile, pid, started_at}`），记下 URL、token、profile 与 pid（pid 连同
   `/proc/<pid>/stat` 里的启动时间一起记，停止前先核对，避免 pid 被复用后误杀；`url` 里的
   token 是插件页唯一的凭据）。写入分两次：进程起来时先写 pid 与启动时间，日志里出现
   `dsh web: <url>` 时补上 url 与 token。这份记录是「启动 token 跨会话记住」那条契约在
   远端的落点：不写它，启动器一重启就丢掉 token，插件页从此只剩「由系统接管」那条死路。
   本机那次认领同样先拿 `running.json` 里的 token 试一次（`native::NativeClient::connect`
   成功才沿用，失败即丢弃），否则「启动器更新或退出重开、实例还在跑」就白丢 token。
4. 停止只在用户要求时发生：向那台机器的**进程组**发 SIGTERM（脱离会话起的实例用 `setsid`，
   它的 pid 就是组号，所以是 `kill -TERM -- -<pid>`），没有组时退回单 pid——只停组长会把它
   起的子进程留下。核对、发信号、确认在**同一次 ssh** 里完成：发信号前先核对 `/proc/<pid>/stat`
   里的启动时间与记下的那份是否一致，不一致就**不发**（pid 被回收后复用了）；这份时间读不到
   时，说清读不到并给出在那台机器上停它的命令，而不是跳过核对直接发信号。确认也在那台机器上
   等，只有确认进程不在了才报「已停止」。停下之后还要追停同一端口上 DSH 自重启出的替代进程，
   否则页面说「已停止」而实例还在应答。身份怎么核对、按什么节奏等、追停几轮，完整语义见
   ADR-0017。

## 后果

- 同一台主机上的实例，行为像「被收养的外部进程」，不像「启动器拉起的子进程」。停机只在
  用户要求时发生：点「停止」、重启、删除实例、删除版本都会先停正在跑的那个进程；退出启动器
  与删除主机记录不停它。
- 远程主机上出现启动器不知道的实例是常态（用户自己 ssh 上去起的、别的启动器起的），
  所以「能不能管理插件」仍然只由 URL 里有没有 token 决定，与进程是谁起的无关。
- 界面上的「已停止」与「主机连不上」必须分开显示：状态说错会让人做出错误的动作——
  看到「已停止」就去点「启动」，于是在服务器上起了第二个（这正是收养机制存在的理由）。
  所以「主机不可达」是 `InstanceState` 的第五个取值，而不是「已停止」的另一种说法；启动时
  那一遍扫描还没问到的机器，它的实例在页面上是「启动中」，也从不是「已停止」。
- 本机也有同一条收养路径：app 启动后在后台跑一遍 `process::adopt_surviving_instances`。被替换 /
  强杀留下的 DSH 进程会一直占着端口，不认领的话界面会一直说「已停止」，直到用户碰巧点一次启动。
  这一遍只看本机——远端实例的端口在那台机器上，本机的探针只能问这台 Mac；远端那一遍是
  `adopt_surviving_remote_instances`，与页面「重试」共用 `settle_remote_instance` 的那份判断。
- 远端启动走 `HostTransport::spawn_detached`，命令行取自 `launch::instance_argv`：绝对 Node
  来自**那台机器自己**的绑定，`--host` 仍然不传，`--no-open` 问那台机器的 bundle。环境取自
  `launch::instance_env_for`：DSH_HOME、实例名、实例自己的变量，再加主机记录里的额外环境
  变量，**不含本机代理**——代理描述的是这台 Mac 的网络出口，远端出口由主机记录决定。启动前要
  问那台机器自己的几件事（`bin.js` 在不在、profile 是不是 web 应用、profile 的 lan-bind
  端口与 pnpm store）全部经传输层，不在本机 `fs` 上照远端路径读。
- 跟随远端日志的那个任务只做两件事：发现 URL、发现进程没了（`remote::tail` 在那台机器上等，
  不是一秒一次 ssh）。
- `kill_all`（退出启动器）跳过远端实例：它们在别人的机器上跑，本来就该活过这一次退出。

## 备选方案

- **照抄本机，退出即停**：被否，见背景。
- **主机记录里给一个「退出时是否停止」的开关**：被否。同一个开关在两种情形下的默认值会
  相反，等于让每个用户先做一次他没有依据做的选择；而这两条规矩各自在自己那台机器上都是
  合理的。

## 修订（2026-11）

决策 §4 原写「按 pid 发 SIGTERM，然后轮询确认」，与代码不符：实现向 `setsid` 的进程组发
（`kill -TERM -- -<pid>`，没有组时退回单 pid），核对、发信号与确认在同一次 ssh 里完成，并且
要追停同一端口上 DSH 自重启出的替代进程。正文已按实现改写；停止的完整语义（身份核对、0.1 秒
轮询、追停上限）记在 ADR-0017。背景里「只有被收养的外部进程活得比启动器久」也不准确——
`kill_all` 对本机被收养的进程同样尽力发一次 SIGTERM。

## 追加（2026-11 注释清理）

- 远端运行表不是一次扫描的结论：启动器起来扫一遍，之后按定时器再扫（process::watch_remote_instances）——那台机器上的 DSH 会自己重启换一个进程，实例也可能由启动器之外的东西拉起，只扫一遍会让它们迟迟不出现在「运行中」。
- 远端运行状态有两处必须串行：运行记录是「读一次、改一条、写回去」，两台实例同时启动会互相覆盖条目，所以写入共用一把锁；读不出来的记录原样留着，按空记录重写会删掉别的实例。状态扫描同一时刻只跑一遍，启动那一遍与周期对账问的是同一个问题，两次答案同跑会让晚到的「已停止」盖掉刚认领的「运行中」。
- 远端日志只追加、启动时不截断：跟随者以 spawn 之前 remote::log_size 量到的字节数为起点，之后每次都落在文件当前大小上，只读这一轮写下的输出；一次最多带 256 KB（MAX_TAIL_BYTES），中间跳过的字节不补。DSH 自重启后 pid 不变而 stdout 换成一个新文件（restart helper 给的临时文件），找地址时要读 /proc/<pid>/fd/1，不能只读启动时记住的日志路径。
