# Profile 模板不碰用户自己的 ~/.dsh

## 背景

新建 Profile 的做法是把一份模板目录复制成新名字：DSH 的 Profile 是目录，里面是插件组合
与补丁文档，没有「从空目录开始」这条路。模板叫 `profiles/__temp__`，是装版本那条任务在
一个全新 DSH_HOME 里留下的：先让 DSH 跑一次生成 `profiles/web`，再把它复制成 `__temp__`
并擦掉那次启动钉住的端口。

麻烦在来源。用户自己的 `~/.dsh` 也是一个能指向的 DSH_HOME，它下面同样有 `profiles/web`
——从它复制模板不但要往用户的数据目录里写 `__temp__`，也把「启动器只写启动必需的事实」
（ADR-0010）那条边界又冲开一个口子。反过来，全新的 HOME 又常常一个模板都没有。

## 决策

**新建 Profile 的模板按固定顺序从三处取，全部在那台机器上；用户自己的 `~/.dsh` 不参与。**

1. 这个 HOME 自己的 `profiles/__temp__`——前提是这个 HOME 不是用户的 `~/.dsh`；
2. 这个 HOME 的 `profiles/web`：先复制成 `profiles/__temp__`、擦掉复制件里 webserver 钉住
   的端口（规则见 ADR-0010），再复制成新 Profile；
3. 那台机器数据目录下 `homes/*/profiles/__temp__` 的第一个——装版本任务在专属 HOME 里留下
   的那一份。

三处都没有就报错「未找到可用的 Profile __temp__ 模板，请先安装至少一个 DSH 版本」，不凭空造。
第 1、2 步对用户默认 HOME 不成立，判定有两处：HOME 记录上的「用户默认」标记，以及在那台机器
上按路径再判一次（远端脚本还比较 `$HOME/.dsh/profiles`）——记录写错也不会让远端把模板写进
用户的 `~/.dsh`。

`__temp__` 与 `node_modules` 是保留名：创建、改名都不让用，删除直接拒绝，列 Profile 时两个
都不出现。本机与远端是同一套规则，远端由 `remote::create_profile` 在同一台机器上做同样的
三步（唯一的差别是它用 awk 擦端口，本机用 `profile::scrub_port_pin`）。

## 后果

- 模板永远不会从 `~/.dsh` 里借：实例指向用户的 HOME，我们既不往里写，也不会找不到模板。
- 只有装过至少一个版本之后才能新建 Profile。全新且空的环境里「找不到模板」是预期结果。
- 模板里的端口钉必须先擦：补丁文档里的端口压过命令行 `--port`，带钉模板派生出的每个实例都
  会抢同一个端口（`EADDRINUSE`），而且只看启动参数看不出来。
- 保留名在任何删除路径上都先被拒绝：它们不属于用户，删了要么让模板机制失效，要么动到 DSH
  自己的依赖布局。
- 模板的第一次生成在装版本任务里（本机 `tasks::ensure_web_profile_template`，远端
  `process::ensure_remote_web_profile_template`），不在新建 Profile 这条路上：这里只取用，
  不起进程。判据分两边：远端看那个 HOME 一个 Profile 都没有；本机只在安装任务新建专属
  HOME 时跑，看模板目录 `__temp__` 在不在（ADR-0006）。

## 备选方案

- **没有模板就当场跑一次 DSH 生成 `web` 再派生**：被否。新建 Profile 不该起进程、占端口、
  耗几秒钟，更不该在用户没准备启动实例时去跑 DSH。
- **从 `~/.dsh` 借模板**：被否。那是最容易「看起来能用」的做法，代价是往用户的数据目录里
  写东西，或者把用户自己放着的 `__temp__` 当成启动器的模板。
