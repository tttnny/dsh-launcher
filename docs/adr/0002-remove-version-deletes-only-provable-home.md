# 删除版本只删位置可证的专属 DSH_HOME

## 背景

删除一个版本时，启动器已经级联删掉了它的实例和安装目录，但版本专属的 DSH_HOME
留在磁盘上，越积越多。

难处在于 `<数据目录>/homes/<版本名>` 和 `~/.dsh` 都是 DSH_HOME，都可能被实例指向
（`~/.dsh` 由启动器自动收录，用户也完全可以手动把实例指过去）。删错一个，删掉的
是真实数据——那下面有 `sessions/`、`storages/`、`.credentials.yaml`。

## 决策

**只删 `<该主机的数据目录>/homes/<版本名>`，且只按路径判定。**

这是唯一一个启动器能**证明**是自己建的路径——`migrate_instances_to_dedicated_homes`
就是照这个规则建的，1 版本 1 目录是它强制的。别的路径一律不碰，哪怕是实例刚用过
的那个。

数据目录是**那台主机自己的**（ADR-0006）：本机的是启动器自己的数据目录，远程主机的
是它在服务器上的那一份。同一个相对路径在两台机器上是两个不同的目录，所以删除要按
主机算、也在那台机器上做——远程由传输层删（`remote::remove_dir`），只删那台主机数据
目录之内的路径；路径相等判定在远端不折叠大小写。

删除前弹确认，确认框里**指名要删的路径**并写明「包含会话历史与凭据」。确认并进现有
的删除流程，不额外增加点击。

## 后果

- `~/.dsh`、用户手工指定过的 HOME、共用的 HOME 都不会被误删——**这是本决策的全部
  意义**。代价是这类 HOME 下的残留需要用户自己清。
- 判断依据是路径而不是「这个 HOME 有没有被引用」，所以先删实例还是先删 HOME 的顺序
  不影响结果。
- 会话历史与凭据确实会丢失，且不可恢复。确认框是唯一的防线。

## 备选方案

- **按实例指向删**：被否。会删掉 `~/.dsh`——用户完全可能把实例指过去，那下面还有
  他别的实例的数据。
- **在 HOME 记录上打「启动器建的」标，按标记删**：被否。要加字段、加迁移，而按路径
  已经能得出同一个结论，收益不抵成本。
- **只删安装目录，HOME 留给用户自己清**：被否。这正是现状，也是提出这个改动的动机。
