# 环境检测以系统环境变量为基准，用户可以手动指定路径

## 背景

启动器为「本机有没有 Node / pnpm」做了一套探测：把继承来的 `PATH` 各段，再接上
nvm / fnm / PNPM_HOME / Homebrew / 官方安装脚本的目录布局，逐个跑 `--version`。

这套探测很能找，但它回答不了用户真正在问的那件事：**我的系统环境变量里有没有。**
用户在终端里敲 `node -v` 报 command not found，启动器却报「环境已就绪」——因为它在
`~/.nvm/versions/node/<版本>/bin` 里找到了。反过来，用户把 PATH 配好了，页面上也看不出
有什么变化。页面只报「有」，不报「从哪来的」，用户既无法判断问题出在哪，也无处可改：
配置里的 `toolchain` 是每次探测都会重写的缓存，前端没有写入通道，页面上也没有任何指定
可执行文件的地方。

## 决策

**环境检测以系统环境变量为基准报结论，用户可以手动指定可执行文件。**

1. 「系统环境变量」定义为**用户登录 shell 的 PATH**（`~/.zshrc` / `~/.zprofile` 里配的
   那一套）。它就是用户在终端里敲 `node -v` 时命中的那个，所以检测另起一个登录 shell
   去读，而不是用启动器自己继承到的环境。
2. 每个工具的结论都带来源：`system`（就来自系统环境变量）、`fallback`（系统环境变量里
   没有，启动器在常见安装目录里找到的）、`manual`（用户指定的）。页面把来源说出来。
3. 系统环境变量里没有时，给用户两条路：直接指定 node / pnpm 的可执行文件，或者去终端
   把它加进 PATH 后点「重新检测」。后者要靠强制重读系统环境变量（跳过探测缓存）兑现。
4. 用户指定的路径写入 `settings.toolchain_overrides`，**优先于一切探测**；`settings.toolchain`
   仍然只是探测缓存，不是用户偏好。
5. 候选顺序固定为「用户指定 → 系统环境变量 → 常见安装目录」，探测与执行共用这一份，
   所以「页面报的」和「实际用的」继续是同一个。

## 后果

- 界面上多出「来源」这一层信息，也多了「手动指定 / 取消指定」两个动作；环境不就绪时的
  安装指引保持原样（缺什么就教装什么），只是旁边多了一条「也可以直接指定」的路。
- 读系统环境变量需要起一个登录 shell（`.zshrc` 只有交互式 shell 会读）。因此这一步有
  超时、有短时缓存（窗口每次获得焦点不必都起一个 shell），「重新检测」按钮绕过缓存。
  探测失败不当作错误：退回启动器继承到的 PATH，并在状态里如实标注没读到 shell。
- 用户指定的文件失效（被删、被换掉）时退回自动探测，但页面上仍然显示它并说明用不了，
  由用户决定是换一个还是取消。
- 指定后立即生效：启动实例、安装版本、源码构建用的是同一个可执行文件，不需要重启启动器。

## 备选方案

- **只用启动器继承到的 PATH 判断**：被否。从 Finder 启动的应用拿到的是最小 PATH，用户
  在 `.zshrc` 里配的东西完全不会出现——页面永远报「没有」，而「配好系统环境变量再检测」
  这条路就永远不会生效。
- **把用户指定写进 `settings.toolchain`**：被否。那个字段每次探测都会重写，用户的选择会
  被下一次探测覆盖，也再分不出「启动器找到的」和「用户要的」。
- **让启动器自己装一份 Node / pnpm**：被否。工具链由用户提供是既有决定，启动器只负责
  找到并驱动它。
- **只在设置页给一个路径输入框**：被否。用户要的是「不知道装在哪」时的出路，输入框要求
  他已经知道路径；文件选择器才是把这件事交还给他的方式。

## 追加：远程主机

远程主机沿用同一套模型（用户指定 → 系统环境变量 → 常见安装目录），补四条：

1. 探测经 ssh 在那台主机上跑**交互式登录 shell**（`bash -ilc`，与本机读 PATH 是同一个形状）
   读 `PATH`，输出用分隔标记包住并设超时——Linux 上把 brew、miniconda 这类目录加进 `PATH` 的
   是 `~/.bashrc`，只有交互式 shell 会读它；只跑登录 shell（`-lc`）会漏掉用户终端里真正命中的
   那一个。页面报的与执行用的是同一份；执行一律用绝对路径，因为靠 `node` 这个名字在非交互会话
   里未必找得到东西。交互式 shell 要起一遍 rc 文件，比非交互慢，所以结论照本机的规矩缓存。
2. 远程**跳过版本低于 20 的 Node 候选**，继续往后找；全都不合才用最后一个，并在页面上报出
   跳过了谁、为什么。
3. 远程的「手动指定可执行文件」只能填路径（远端没有本机文件选择器），校验方式不变：经 ssh
   真的跑一次 `--version` 才认。
4. 「常见安装目录」换成 Linux 的那一套：Linuxbrew（`/home/linuxbrew/.linuxbrew/bin`、
   `~/.linuxbrew/bin`）、nvm / fnm 的版本目录、pnpm 官方脚本的目录（`~/.local/share/pnpm`）、
   `~/.local/bin`、`/usr/local/bin`。这一条不是可有可无的兜底：在只有交互式 shell 才配 `PATH`
   的机器上，它是唯一还能把工具找回来的地方。

第 2 条只对远程生效，本机维持「只告警不阻止」：本机是用户自己的桌面，他有上下文，也有动手
改的自由；远程是选错就白跑一趟的地方。真实例子：一台远程主机上登录 shell 先撞到 apt 装的
Node 18，而 Homebrew 里躺着 Node 26，可 DSH 有代码路径要 `node:sqlite`（Node 22.5+）。
